# ТЗ: Спільні списки покупок (React Native + Firebase)

**Стек:** React Native (Expo, TypeScript) · Firebase Authentication · Cloud Firestore · Firebase Emulator Suite
**Час:** 1 день, ≈ 6 годин чистої роботи
**Формат здачі:** Git-репозиторій + README

---

## 1. Мета завдання

Мобільний застосунок, у якому користувачі ведуть списки покупок і діляться ними з іншими. Зміни одного користувача миттєво з'являються в іншого.

> **Реальний Firebase-проєкт не потрібен.** Усе працює локально через Firebase Emulator Suite (Auth + Firestore) з demo-проєктом. Окрім ручного тестування в застосунку, безпека даних перевіряється автоматичними тестами правил.

---

## 2. Пріоритети

Якщо часу бракує, цей порядок важливіший за повноту:

1. **Обов'язково:** авторизація, списки, елементи списку з realtime-синхронізацією, правила безпеки + тести правил.
2. **Бажано:** шеринг списку з іншим користувачем, обробка станів завантаження та помилок.
3. **Бонус:** пункти розділу 7.

Краще повністю закрити 1 і 2, ніж частково все.

## 3. Функціональні вимоги

### 3.1. Авторизація

- реєстрація та вхід за email і паролем;
- сесія зберігається між перезапусками застосунку;
- вихід з акаунта;
- зрозумілі повідомлення про типові помилки (невірний пароль, зайнятий email, слабкий пароль, немає мережі).

### 3.2. Списки

- створення, перейменування та видалення списку;
- користувач бачить свої списки та списки, якими з ним поділились, в одному екрані;
- видаляти список і керувати доступом може лише власник;
- екран списків оновлюється в реальному часі.

### 3.3. Елементи списку

- додавання елемента (назва, необов'язкова кількість);
- позначення як куплений / не куплений, видалення;
- некуплені елементи вгорі, куплені внизу;
- у заголовку списку видно прогрес (скільки куплено з загальної кількості);
- зміни, зроблені одним користувачем, з'являються в іншого без перезавантаження (перевір на двох симуляторах або на симуляторі та Expo Go).

### 3.4. Шеринг

- власник додає іншого зареєстрованого користувача до списку за email;
- учасник бачить список і може змінювати елементи, але не може видалити список чи змінити склад учасників;
- власник може прибрати учасника.

Зверни увагу: клієнтський SDK не дозволяє шукати користувачів Firebase Auth за email, тож тобі потрібно придумати, як це вирішити в межах Firestore.

### 3.5. Правила безпеки Firestore

Напиши `firestore.rules`, які гарантують:

- користувач не може прочитати чи змінити чужий список;
- права власника й учасника відрізняються, як описано вище;
- дані, що записуються, мають очікувану структуру (типи та обов'язкові поля, адекватні обмеження довжини);
- неавторизований користувач не має доступу ні до чого.

Правила покрий автоматичними тестами (мінімум 6 сценаріїв: allow і deny для власника, учасника, стороннього, анонімного).

### 3.6. Стани інтерфейсу

Для кожного екрана з даними: стан завантаження, порожній стан і стан помилки. Форми не дозволяють подвійне відправлення. Клавіатура не перекриває поля вводу.

## 4. Технічні вимоги

- Firebase JS SDK (modular API), без нативних Firebase-модулів;
- підключення до емуляторів керується конфігурацією, у коді немає хардкоду на кшталт `if (__DEV__)` з вшитими адресами;
- доступ до емуляторів з Android-емулятора, iOS-симулятора та фізичного пристрою відрізняється: розберись, як це працює, і опиши в README;
- навігація: React Navigation або expo-router (на вибір);
- робота з Firestore винесена з компонентів (хуки або сервісний шар);
- TypeScript у режимі `strict`, лінтер без помилок;
- ніяких секретів у репозиторії.

## 7. Бонус (за бажанням)

- офлайн-поведінка: що бачить користувач без мережі та як це відображається в UI;

- темна тема;
- перетягування для зміни порядку;
